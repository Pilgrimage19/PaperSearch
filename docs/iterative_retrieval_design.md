# 迭代检索方案设计（多 Agent 协作）

> 目标：把当前「单轮检索」升级为「多轮迭代」，解决召回率 27% 的瓶颈
> 核心创新：**Critic（检索自省）Agent** —— 显式诊断「约束覆盖缺口」，针对性补检索

---

## 1. 现状与问题

当前检索是**单轮、一次性**的：

```
Step 1 查询理解 → Step 2 混合检索（一次性召回）→ 结束
```

问题：如果 GT 论文在第一次召回时没被「关键词/语义查询」匹配到，就**永远丢了**——后续没有第二次机会。这是召回率 27% 的根因。

而赛题明确要求：

> **「支持迭代式检索策略：根据已找到的相关论文信息，动态调整检索策略和关键词」**

这正是我们现在缺的。

## 2. 设计目标

把检索从「单轮」改成「多轮迭代循环」，让系统能：
1. 召回一批论文后，**反思**这次召回够不够、缺口在哪
2. 针对缺口**动态调整查询**，再召回
3. 循环直到覆盖充分或达到上限

## 3. Agent 架构（4 个 Agent）

参考 SPAR 的 5-Agent 设计 + PaSa 的 Crawler/Selector，精简为 4 个，其中 **Critic 是核心创新**：

| Agent | 职责 | 对应现有代码 | 类型 |
|-------|------|-------------|------|
| **Planner（规划器）** | 查询理解、约束分解、初始检索计划 | Step 1 | LLM |
| **Retriever（检索器）** | 混合检索（关键词+语义+引文遍历） | Step 2 | 无 LLM（API+向量） |
| **Critic（自省器）** | 诊断「约束覆盖缺口」，生成补充查询 | **新增** | LLM |
| **Selector（筛选器）** | 过滤不相关论文，精排 | Step 3 | LLM |

## 4. 迭代流程

```
                    ┌─────────────────────────────┐
                    │  Planner：查询理解 + 约束分解  │
                    │  （约束 C1 方法 / C2 任务 / C3 数据 ...）│
                    └──────────────┬──────────────┘
                                   │ 初始查询
                                   ▼
                    ┌─────────────────────────────┐
              ┌────▶│  Retriever：混合检索（召回候选） │
              │     └──────────────┬──────────────┘
              │                    │ 候选池
              │                    ▼
              │     ┌─────────────────────────────┐
              │     │  Critic：约束覆盖自省          │
              │     │  - C1 方法 覆盖了吗？          │
              │     │  - C2 任务 覆盖了吗？          │
              │     │  - C3 数据 覆盖了吗？          │
              │     └──────────────┬──────────────┘
              │                    │
              │        覆盖充分？   │ 覆盖不足
              │        ┌───────────┴───────────┐
              │        │                       │
              │        ▼                       ▼
              │      （结束）          生成「缺口查询」
              │                        （针对未覆盖的约束）
              └────────────────────────┘
                                   │
                            （最多迭代 N 轮）
                                   │
                                   ▼
                    ┌─────────────────────────────┐
                    │  Selector：过滤 + 精排         │
                    └─────────────────────────────┘
```

## 5. Critic 的核心逻辑（创新点）

Critic 是让系统「知道自己在找什么、找没找到」的关键。它做两件事：

### 5.1 约束覆盖检查

输入：原始查询 + 约束列表 + 当前候选池（标题/摘要）

对每个约束维度，判断候选池里是否有「充分覆盖」该维度的论文：

```json
{
  "coverage": [
    {"constraint": "method: BERT-based", "covered": true,  "evidence": "候选池有 12 篇 BERT 相关论文"},
    {"constraint": "data: Chinese social media", "covered": false, "evidence": "几乎没有涉及中文社交媒体的论文"}
  ],
  "verdict": "incomplete",
  "gaps": ["data: Chinese social media"]
}
```

### 5.2 缺口查询生成

对「未覆盖」的约束，生成针对性查询（语义扩展、同义词、下位词）：

```
缺口 "data: Chinese social media"
  → "Weibo sentiment analysis dataset"
  → "Chinese short text sentiment classification"
  → "中文社交媒体情感分析"
```

### 5.3 Critic 的 Prompt 设计

```python
CRITIC_PROMPT = """
你是学术检索的自省器。给定查询的约束列表和当前检索到的论文池，
判断每个约束是否已被充分覆盖，并针对未覆盖的约束生成补充查询。

Query: {query}
Constraints: {constraints_json}
当前候选池（前 N 篇标题+摘要）: {paper_list}

输出 JSON:
{
  "coverage": [{"constraint": "...", "covered": true/false, "evidence": "..."}],
  "verdict": "complete" / "incomplete",
  "new_queries": ["针对缺口的补充查询1", "查询2"]
}
"""
```

## 6. 迭代终止条件

满足任一即停止：

1. **覆盖充分**：Critic 返回 `verdict: "complete"`（所有约束都覆盖）
2. **达到最大轮数**：默认 3 轮（可配）
3. **候选池饱和**：新召回论文数 < 阈值（说明已搜无可搜）

## 7. 成本控制

| 环节 | LLM 调用 | 说明 |
|------|:--:|------|
| Planner | 1 次 | 查询理解 |
| Critic | 每轮 1 次 | 最多 N 轮 = N 次 |
| Selector | 1-2 次 | 精排 |

**总 LLM 调用：3-5 次/查询**（原 2-3 次），增加 ~2 次 Critic 调用，成本可控。

检索 API 调用由「检索增量」控制——每轮只对「缺口查询」检索，不重复检索已覆盖的维度。

## 8. 与现有代码的衔接

| 现有 | 改动 |
|------|------|
| `step1_query_understanding.py` | 保留（Planner） |
| `step2_hybrid_retrieval.py` | 拆成「单轮检索函数」+「迭代编排」 |
| **新增 `step2b_critic.py`** | Critic 自省 + 缺口查询生成 |
| `step3_ranking.py` | 保留（Selector） |

核心改动是把 `step2` 从「一次性」改成「可被循环调用的单轮检索」，外面套一个迭代编排循环。

## 9. 创新点总结（答辩用）

| 创新点 | 说明 | 区别于现有系统 |
|--------|------|---------------|
| **Critic 约束覆盖自省** | 显式诊断每个约束维度的覆盖情况 | PaSa 用 RL 隐式学「何时停」；SPAR 无自省，靠固定轮数 |
| **缺口驱动的查询生成** | 只对未覆盖约束补检索，不盲目扩查询 | SPAR 的 Query Evolver 无方向地生成 3 类查询 |
| **轻量迭代（无需 RL）** | 用 LLM 自省代替 RL 训练 | PaSa 需 8×H100 RL 训练，我们零训练 |

## 10. 实现路线

1. 把 `step2` 的检索逻辑封装成 `retrieve_once(queries)` 可复用函数
2. 新增 `critic.py`：约束覆盖检查 + 缺口查询生成
3. 新增迭代编排：`for round in range(max_rounds): 检索 → 自省 → 补检索`
4. 候选池跨轮累积，去重
5. 迭代结束后进 Step 3 排序
